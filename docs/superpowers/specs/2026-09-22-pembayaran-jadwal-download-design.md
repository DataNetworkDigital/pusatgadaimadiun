# PGM: Partial Payments, Cash, Payment Corrections, Schedule Changes, Export Columns — Design

Date: 2026-09-22
Status: Approved section by section in chat by Gde; awaiting review of this written spec
Repo: DataNetworkDigital/pusatgadaimadiun (deploys to GitHub Pages on every push to `main`)

## 1. Goal

Seven owner requests, all about how project money is recorded and reported:

| # | Request (owner's words, paraphrased) | Covered by |
|---|---|---|
| 1 | One month's bagi hasil paid in parts (part on the 5th, rest on the 6th), or the unpaid part doubled into next month | Part B |
| 2 | No option to receive **cash** for bagi hasil or pelunasan | Part B |
| 3 | Fix a wrong confirmation: wrong month, money never arrived, wrong amount/account/date | Part B |
| 4 | Download: choose which columns; dates missing (page `/project`) | Part A |
| 5 | Pelunasan pushed back by X months | Part C |
| 6 | Partial payment / partial pelunasan, with a choice for the remainder | Part B + Part C |
| 7 | Installment payments, with a flag when bagi hasil is not fully paid | Part B |

## 2. Decisions made with Gde

| Topic | Decision |
|---|---|
| Partial payment model | Receipts allocated to schedule rows ("cicilan per tagihan"). Rows keep their original tagihan. |
| Default allocation | Oldest open row first; any excess spills to the next rows. Target row can be chosen manually. |
| Cash | A "Tunai" option in every money-in sheet, backed by an auto-created `Kas/Tunai` account. |
| Legacy underpaid rows | Stay LUNAS (legacy waiver). Gde gets a list of them to reopen any that were truly short. |
| Corrections | Per receipt: Edit, Pindah ke bulan lain, Batalkan. |
| Remainder on a bagi hasil row | Terima pembayaran lagi / Gabung sisa ke bulan depan / Anggap lunas. |
| Partial pelunasan | Ask for the remainder: Ditagih menyusul / Diperpanjang (base = remainder) / Kontrak baru. |
| Extension start | Chosen per case: "mulai hari itu" (default) or "mulai bulan depan". |
| Extension rate | Prefilled with the project's month-4+ rate, editable. |
| Rollover first-month bagi hasil | Chosen per case: charged on the contract date (default, amount editable) or not charged. |
| Rollover and DanaTrack | Not synced to DanaTrack. Telegram notification still sent, labelled "Kontrak lanjutan". |
| Export | Column picker for Excel, PDF and Daftar Tagihan; date columns added; NIK off by default; last choice remembered per device. |

## 3. Current state (verified in code, 2026-09-22)

- A schedule row (`project.payments[]`) is binary: `receivedAmount != null` means paid. One row = one income transaction.
- Underpaying a row records the lower amount and still marks it paid. The shortfall is lost.
- `updateProjectPayment` already edits amount/account/date of a paid row. There is no way to un-confirm or move a confirmation.
- `Kas/Tunai` exists as a bank preset in `AccountForm`, but money-in sheets require picking an existing account.
- `updateProject` allows duration edits after payments (unpaid rows are regenerated by `recomputeUnpaidSchedule`) but blocks principal changes.
- The projects PDF (`exportProjectsToPdf`) has no date columns at all; its `Return/bln` column shows only tier 1. Excel and Daftar Tagihan already have dates.
- **Existing bug:** `deleteTransaction` / `updateTransaction` handle `debtId` but not `projectId`. Deleting or editing a project transaction from the Transaksi page changes the account balance but leaves the project row marked paid.
- Business convention: one month of bagi hasil is deducted up front from the disbursement (`disbursedAmount = principal − tier1%`), so rows 1..N−1 are bagi hasil and row N is pelunasan (principal only).
- No automated test runner in the repo.

## 4. Delivery plan

Three parts, three implementation plans, executed in order. Each part is built on its own branch, verified in demo mode, and merged to `main` (which deploys) only with Gde's go-ahead.

1. **Part A — Export columns.** Small, touches no data.
2. **Part B — Payment model.** The foundation for Part C. Includes the one-time data migration.
3. **Part C — Schedule changes.** Mundur X bulan, partial pelunasan choices, rollover.

## 5. Part A — Export column picker

- New pure module `src/utils/exportColumns.js`: a registry of columns, each `{ key, label, get(project, ctx), align, width, sensitive?, defaultOn }`.
- Columns: No · Nama project · Pemilik · No. Kontrak · Status · Tanggal Mulai · Tanggal Berakhir · Jatuh Tempo Berikutnya · Durasi · Nilai Project · Modal Keluar · Bagi hasil % · Sudah Diterima · Sisa Tagihan · Net · No. HP · Alamat · Agunan · NIK · Rekening Sumber · Catatan. (Part B adds **Kurang Bayar**.)
- Default on: the columns the PDF shows today, plus Tanggal Mulai, Tanggal Berakhir, Jatuh Tempo Berikutnya. NIK is `sensitive` and off by default.
- `ExportSheet` gets a "Pilih kolom" step after the user picks Excel, PDF, or Daftar Tagihan. Selection is stored in `localStorage` per export type (wrapped in try/catch; falls back to defaults).
- PDF uses the selected columns, switches to landscape when the selected widths exceed portrait width, and stretches one flexible column (Nama/Alamat) to fill the page, as Daftar Tagihan does now.
- `Bagi hasil %` shows both tiers, e.g. `5,5% / 6,5%`; legacy flat-rate projects show one value.
- Dates use the existing `formatDate`. "Tanggal Berakhir" = contractual end (start + durasi on the payment day), reusing the helper Daftar Tagihan already uses, falling back to the last schedule row when duration is missing; "Jatuh Tempo Berikutnya" = earliest open row.
- Excel's project sheet uses the same selection. Its payment-schedule sheet is unchanged in Part A.

## 6. Part B — Payment model

### 6.1 Data (inside the project document)

```
payments[]                    schedule rows (existing)
  no, dueDate, type: 'interest' | 'final', expectedAmount, ratePct
  baseAmount?                 principal basis (Part C rows only)
  extensionId?                set on rows created by an extension (Part C)
  closure?                    how an unpaid remainder was closed, at most one:
    { kind: 'carry',    amount, toNo, at }            merged into a later row
    { kind: 'waive',    amount, reason: 'manual'|'legacy'|'settlement', note?, at }
    { kind: 'extend',   amount, extensionId, at }     Part C
    { kind: 'rollover', amount, projectId, at }       Part C
  receivedAmount, receivedDate      DERIVED, rewritten on every change (back-compat)
  transactionId, accountId          DERIVED from the latest receipt (back-compat)

receipts[]                    new: one entry per money-in event
  id, amount, date, accountId, transactionId, createdAt
  allocations: [{ no, amount }]     sums to `amount`
```

Every receipt has exactly one income transaction (`type: 'income'`, `toAccount`, `projectId`, new field `receiptId`, `paymentNo` = first allocated row for back-compat). Account balances and dashboard Masuk/Keluar therefore keep working exactly as today.

### 6.2 Status rules (single source: `src/utils/paymentStatus.js`)

```
rowDue(row)        = row.expectedAmount + Σ closure.amount of rows whose closure is { kind:'carry', toNo: row.no }
rowAllocated(row)  = Σ allocations for row.no across all receipts
rowRemaining(row)  = max(0, rowDue − rowAllocated − (row.closure?.amount ?? 0))
state   = 'lunas'  when rowRemaining = 0
          'kurang' when rowAllocated > 0 and rowRemaining > 0
          'belum'  when rowAllocated = 0 and rowRemaining > 0
overdue = rowRemaining > 0 and dueDate < today
```

Display: a `carry` closure shows "Digabung ke bulan j"; `waive` with reason `legacy` shows plain LUNAS; other waivers show "Dianggap lunas". A project is complete when every row has `rowRemaining = 0`.

Every place that today treats `receivedAmount != null` as paid switches to these helpers (see 6.7).

### 6.3 Allocation (pure: `src/utils/allocation.js`)

- Open rows ordered by due date, then `no`. Start at the chosen row (default: oldest open row).
- Fill each open row up to its `rowRemaining`, then move to the next.
- Amount left after the last open row → reject: "Jumlah melebihi total sisa tagihan (Rp X)".
- Editing or moving a receipt re-allocates that receipt only; other receipts never move silently.

Example: bulan 3 tagihan 5,5jt. Receipt 3jt on 5 Okt → bulan 3 KURANG 2,5jt. Receipt 1jt on 6 Okt → KURANG 1,5jt. Next month a receipt of 7jt → bulan 3 LUNAS (1,5jt) and bulan 4 LUNAS (5,5jt).

### 6.4 Operations (in `DataContext`, each one atomic `writeBatch`)

| Operation | Effect |
|---|---|
| `recordReceipt(projectId, { amount, date, account, startNo? })` | Creates the transaction, credits the account, adds the receipt with allocations, rewrites derived fields, completes the project when all rows are lunas. `account` may be `'cash'`. |
| `updateReceipt(projectId, receiptId, { amount, date, account })` | Reverses the old balance effect and applies the new one (same netting logic as today's `updateProjectPayment`), updates the transaction, re-allocates. |
| `moveReceipt(projectId, receiptId, startNo)` | Re-allocates starting at another row ("salah bulan"). No money moves. Updates the transaction's `paymentNo` and description. |
| `cancelReceipt(projectId, receiptId)` | Deletes the transaction, debits the account, removes the receipt. Rows reopen. A project completed by payments returns to `active` and `closedAt` is cleared. |
| `closeRemainder(projectId, no, { kind: 'carry' \| 'waive', note })` | Carry: only for bagi hasil rows with a later open row; target = next open row. Waive: remainder marked settled. |
| `reopenRemainder(projectId, no)` | Removes a `carry` or `waive` closure. |

Receipts on projects closed by early settlement, macet, or rollover cannot be edited or cancelled in this version; the UI explains why.

A receipt allocated to a row that has a `closure` cannot be edited, moved, or cancelled until that closure is reopened (carry/waive via `reopenRemainder`, extend via "Batalkan perpanjangan"). Otherwise the stored closure amount would go stale and could silently forgive or double-count money.

`settleProjectEarly` changes: keeps rows that have allocations; their remainders get `closure { kind:'waive', reason:'settlement' }`; drops rows without allocations; records the settlement as a receipt on a new final row. The default settlement amount adds any outstanding kurang to today's rule (disbursed + current-month bagi hasil).

`closeProjectAsDefault` computes total received from receipts. `deleteProject` claws back **every receipt** (not every row), so split payments are fully reversed.

### 6.5 Cash (Tunai)

- Every money-in sheet (receipt, early settlement, macet recovery, Part C sheets) lists **Tunai** first, then the accounts.
- On submit, `'cash'` resolves to the first account with `kind: 'cash'`, else the first whose name (case-insensitive, trimmed) is `kas/tunai`, `kas`, or `tunai`. If none exists, it is created inside the same batch (`{ name: 'Kas/Tunai', accountNumber: '', kind: 'cash', balance: <amount> }`).
- Cash on hand therefore shows in Rekening and in dashboard totals.

### 6.6 UI

Project detail, per schedule row:
- Header: bulan ke-n, jatuh tempo, jenis, tagihan; an extra line "+ tunggakan bulan k Rp X" when a remainder was carried in; state pill (LUNAS / KURANG Rp X / BELUM / Telat / Digabung / Dianggap lunas).
- Receipts under the row: tanggal · rekening · nominal (split receipts show "sebagian dari Rp X"). Actions: Edit, Pindah ke bulan lain, Batalkan (each behind `ConfirmDialog`).
- Row actions while `rowRemaining > 0`: Terima pembayaran; Gabung sisa ke bulan depan; Anggap lunas (shows the nominal being waived). The final row gets "Atur sisa pelunasan" instead of Gabung (Part C).

Receipt sheet (replaces `PaymentConfirmSheet` for new payments): nominal (default = remaining of the target row), rekening with Tunai, tanggal, "Untuk tagihan" (default oldest open), and a live allocation preview ("Menutup: bulan 3 sisa 1,5jt + bulan 4 sebagian 2jt").

Project list card: badge "Kurang Rp X" = Σ `rowRemaining` over rows in state `kurang`. Overdue unpaid rows keep today's Telat signal.

Daftar Tagihan: one line per open row; nominal = `rowRemaining` (not the full tagihan); status Kurang for partial rows; carried rows are not listed separately (their amount is on the target row).

Exports: new column **Kurang Bayar**; **Sisa Tagihan** uses the new rules.

### 6.7 Touchpoints (all switch to `paymentStatus` helpers)

`DataContext.jsx`, `projectSchedule.js` (`projectSummary`, `findNextDuePayment`, `recomputeUnpaidSchedule`), `projectExport.js`, `CalendarGrid.jsx`, `DayDetail.jsx`, `DashboardPage.jsx`, `ProjectList.jsx`, `ProjectCard.jsx`, `ProjectDetail.jsx`, `ProjectForm.jsx` (capital lock = "has any receipt"), `PaymentConfirmSheet.jsx`, `SettleProjectSheet.jsx`, `CloseProjectSheet.jsx`, `demoSeedData.js`, `demoReset.js`.

`recomputeUnpaidSchedule` must keep rows that have allocations or a closure, and must never regenerate rows that carry an `extensionId`.

### 6.8 Transaksi page guard (fixes the existing bug)

- `TransactionDetail`: for a transaction with `projectId`, hide Edit and Hapus and show "Transaksi ini milik project X. Ubah atau batalkan dari halaman project." with a link to `/project/:id`.
- `deleteTransaction` / `updateTransaction` throw when `tx.projectId` is set (defence in depth).

### 6.9 Data migration

- `src/utils/normalizeProject.js` (pure): if a project has no `receipts`, derive them in memory from legacy rows. Applied when snapshots are read, so unmigrated documents always render correctly.
- One-time script `scripts/migrate-receipts.mjs` (Node, same anonymous-auth pattern used for earlier data fixes):
  - Dry run by default. Writes a JSON backup of every project first.
  - Report: counts; **underpaid rows** (project, bulan, tagihan, diterima, selisih) for Gde; **rows marked paid whose transaction no longer exists** (damage from the Transaksi-page bug).
  - `--apply`: for each legacy paid row, one receipt `{ id: 'legacy-<no>', amount: receivedAmount, date: receivedDate, accountId, transactionId, allocations: [{ no, amount }] }`; underpaid rows get `closure { kind:'waive', reason:'legacy' }`; transactions get `receiptId`. No balances change. Idempotent (projects that already have `receipts` are skipped).
  - Runs on real and `demo_*` collections. `demoSeedData` is updated to the new shape so the daily demo reseed stays consistent.
  - `--apply` on production only after Gde has seen the dry-run report and said yes.

## 7. Part C — Schedule changes

### 7.1 Mundur X bulan / Perpanjang (pure generator: `src/utils/extension.js`)

`buildExtensionRows({ firstNo, anchorDue, paymentDay, months, ratePct, baseAmount, startMode })`:
- `startMode 'today'`: first bagi hasil row due on `anchorDue`. `'nextMonth'`: due one month after `anchorDue`.
- `months` bagi hasil rows, monthly, each `expectedAmount = round(baseAmount × ratePct / 100)`, then one final row (`expectedAmount = baseAmount`) one month after the last bagi hasil row.
- Due dates use `pickPaymentDate` with the project's payment day.

Mundur X bulan (button on active projects next to Pelunasan dipercepat and Macet): allowed while the final row has no allocations. The old final row is replaced by the generated rows starting at its `no`; `anchorDue` = its due date; `baseAmount` = project principal. Sheet fields: jumlah bulan, persen (prefilled with month-4+ rate), mulai hari itu / bulan depan, catatan; live preview of the new rows and end date. Stored as `extensions[] { id, at, kind: 'mundur', months, ratePct, startMode, baseAmount, note, firstNo, replacedRows }`.

Worked example (100jt, pelunasan 5 Okt, 2 bulan, 6,5%): today → 5 Okt bagi hasil 6,5jt, 5 Nov bagi hasil 6,5jt, 5 Des pelunasan 100jt. Next month → 5 Nov, 5 Des bagi hasil, 5 Jan pelunasan.

Guards: once a project has an extension, schedule-affecting fields in Edit Project are locked with the message "Jadwal sudah diubah lewat Mundur/Perpanjang." "Batalkan perpanjangan" undoes the latest extension when none of its rows has allocations: it removes the generated rows, restores `replacedRows` (kind `mundur`), and removes the final row's `extend` closure (kind `sisa`). Project detail lists each extension ("Dimundurkan 2 bulan pada 5 Okt 2026").

### 7.2 Partial pelunasan

After a receipt leaves the final row in state `kurang`, a sheet asks "Sisa pelunasan Rp X mau diapakan?" (also reachable later via "Atur sisa pelunasan"):
1. **Ditagih menyusul** — nothing changes; the row stays KURANG.
2. **Diperpanjang** — same sheet as 7.1 with `baseAmount` = remainder, `kind: 'sisa'`. The final row gets `closure { kind:'extend', amount: remainder, extensionId }`; generated rows are appended after it with `anchorDue` = its due date.
   Example (30 of 100jt paid on 5 Okt, 2 bulan, 6,5%): today → 5 Okt bagi hasil 4,55jt, 5 Nov bagi hasil 4,55jt, 5 Des pelunasan 70jt. Next month → 5 Nov, 5 Des bagi hasil, 5 Jan pelunasan 70jt.
3. **Kontrak baru** — see 7.3.

### 7.3 Kontrak baru (rollover)

- Opens `ProjectForm` prefilled: name "<old name> (lanjutan)", owner, HP, NIK, alamat, agunan copied; nilai project = remainder; modal keluar = remainder, locked and labelled "Modal dialihkan (tidak ada uang keluar)"; tanggal mulai = date of the partial payment (editable); tiers, durasi and tanggal pembayaran copied (editable); source account hidden.
- Toggle "Tagih bagi hasil bulan pertama di hari kontrak" (default on, amount editable, default = remainder × tier1%). When on, the schedule starts with an extra bagi hasil row due on the start date; later rows keep their normal month-based rates.
- Save, in one batch: create the new project with `fundingMode: 'rollover'` and `rolledFromProjectId` (no funding transaction, no account debit); set the old final row's `closure { kind:'rollover', amount, projectId }`, old status `completed`, `closedAt`, `rolledOverToProjectId`.
- Side effects: Telegram notification labelled "Kontrak lanjutan dari <old>"; `syncToDanaTrack` skipped.
- Both detail pages link to each other.

### 7.4 Accounting invariants

- Account balances and dashboard Masuk/Keluar change only through transactions. Closures, extensions and rollovers create none.
- Per-project net = cash received + rolled-out amount − disbursed (disbursed is non-cash for rollover projects). Summed across a rollover chain, it equals the real cash movement.
- "Total Modal Keluar" in exports counts cash disbursements only (excludes `fundingMode: 'rollover'`).

## 8. Error handling

- All multi-document changes in one `writeBatch`, as today. Validation messages in Indonesian. Submit buttons disabled while saving.
- Guard rails: amounts > 0; allocation never exceeds open remainders; no carry from the final row; no edit/cancel on receipts of closed-by-settlement/macet/rollover projects; no edit/move/cancel on receipts feeding a row with a closure; no extension while the final row is lunas.

- Add `vitest` as a dev dependency and an `npm test` script. Table-driven unit tests for the pure modules: `paymentStatus`, `allocation`, `extension`, `normalizeProject`, `exportColumns`, including every worked example in this spec.

## 10. Rollout and safety

- One branch per part. Merge to `main` (= deploy) only after Gde says go.
- Migration `--apply` only after Gde reviews the dry-run report; backup kept.
- After each release, a short plain-language note to Gde about what changed.

## 11. Out of scope

- Late fees (denda).
- Changing the tier rules.
- DanaTrack changes.
- Firestore security hardening. Separate issue: rules only require `signedIn()` and the app signs in anonymously, so real data is readable and writable by anyone. Tracked separately.
